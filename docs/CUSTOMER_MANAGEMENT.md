# 고객사·회원·자산 조회

## 현재 구현

- 고객사 마스터, 신규 등록 신청, 회원별 조회자/관리자, 변경 감사 이력은 DB에 저장한다.
- `Customer.status`: PENDING(이관 확인 필요), ACTIVE, SUSPENDED. 사업자번호 없는 PENDING은 검색·로그인에 사용할 수 없다.
- 사업자번호는 하이픈 제거 10자리, 체크섬 검사, 고객사 마스터 UNIQUE. 신청은 번호를 선점하지 않으며 같은 번호의 기존 고객사에 연결할 때 MRS의 명시적 선택이 필요하다.
- 기존 회사 가입: `customerType: "existing", customerId`. 신규: `customerType: "new", customer: {name,businessNumber,representativeName,address,phone}`. 공통 필드는 email/password/managerName/managerPhone. 이외 권한·상태 필드는 거부한다.
- 모든 가입은 PENDING. 고객사 신청 승인 후에도 회원은 PENDING이며 MRS의 별도 소속 승인이 필요하다.
- 고객사 역할은 VIEWER/MANAGER. 플랫폼 ADMIN 권한과 무관하다. 이번 릴리스에서는 두 고객 역할 모두 실제 자산 읽기만 제공한다.
- 회사/회원 정지·회원 소속/역할 변경 시 버전을 증가시키고 매 요청 DB 상태와 서명 토큰 버전을 비교한다. 정지 복구 후에도 재로그인해야 한다.

## 고객 포털 내 자산 (2026-10-08)

### 적용 범위

- 시안 `https://sungminmo.github.io/mrs2.0/`의 내 자산 화면을 기준으로 녹색 평가금액 영역, 상태별 바로가기, 최근 자산과 목록의 검색·사진·등급·상태 디자인을 적용했다. 1depth 메뉴는 내 자산, 마켓, 마이페이지이며 내 자산의 내부 탭은 자산 현황·자산 목록·판매 요청 내역이다. 기존 `overview`와 `assets` 화면은 유지한다.
- 내 자산에는 검수·폐기 내역 탭과 자산 등록·입고 신청 버튼을 두지 않는다. 기존 입고 신청과 검수·폐기 업무는 마이페이지의 이용 내역에 유지한다. 자산 상세의 기존 조회·판매 요청 기능과 업무 권한은 변경하지 않는다.
- 프론트만 변경했다. 기존 자산 목록·요약·상세 API를 재사용하며 백엔드, API 계약, DB 스키마·데이터, 배포는 변경하지 않는다. 정적 시안 데이터나 존재하지 않는 지표로 실제 집계를 대체하지 않는다.

### 자산·마켓 공통 검색 모듈

- 자산 목록과 마켓은 `src/DetailSearch.tsx`를 함께 사용한다. 상세 검색 헤더, 적용된 조건 수, 접이식 상세 필터, 검색어 지우기, 초기화·검색 버튼과 모바일 배치가 동일하다. 닫힌 필터는 `inert`로 키보드 접근을 차단한다.
- 자산 필터는 자산 상태(보관 상태·판매 상태·S/A/B/F 등급·정렬), 분류·보관 위치(6자리 카테고리 코드·최대20자리 위치 코드), 등록 기간·경과일(시작/종료 날짜·최소/최대 일수)로 구성한다. 마켓은 기존 카테고리 선택·S/A/B 등급·기획전 조건을 유지한다.
- 입력은 검색 버튼 또는 Enter로 적용하고 1페이지부터 조회한다. 초기화는 적용된 조건뿐 아니라 아직 적용하지 않은 입력도 지운다. 자산 검색의 페이지 크기와 기존 API 계약·권한은 유지한다.
- 고객용 전체 분류·위치 선택 데이터는 아직 제공되지 않아 자산의 코드 입력을 유지한다. 마켓의 판매 가능 상품 분류나 현재 자산 페이지로 전체 자산 필터 선택지를 대신 만들지 않는다. 이름 기반 선택은 아래 후속 작업으로 남긴다.

## 고객 포털 판매 요청 내역 (2026-10-08)

### 적용 범위

- 위치는 **내 자산 > 판매 요청 내역**이다. 마켓은 구매 탐색, 마이페이지는 계정·입고·구매 내역을 담당하며 소유 자산의 판매 요청은 내 자산에서 관리한다.
- 기존 이용 내역의 공통 제목·진행 순서 스타일을 재사용한다. 판매 요청 → 상세 검수 → 판매 승인 → 마켓 판매는 일반적인 절차이며 개별 요청의 진행률이나 판매 완료를 뜻하지 않는다. 자산 현황·자산 목록과 같은 탭 선택 및 브라우저 뒤로 가기 동작을 사용하며 모바일에서 탭이 줄바꿈된다.
- 이전 프론트 전용 단계의 조회 준비 화면을 실제 검색·목록·전체 상태별 건수·페이지 이동·현재 페이지 CSV로 연결했다. 판매 요청은 자산당 한 건이며 요청 수량이 이미 저장되어 있어 기존 `GET /api/assets`와 `GET /api/assets/{id}`를 확장했다. 별도 고객 판매 요청 목록·상세 엔드포인트와 DB 마이그레이션은 추가하지 않는다.
- 요청번호 또는 자산을 선택하면 기존 자산 상세로 이동하고 목록 복귀 시 판매 요청 검색·페이지 조건을 유지한다. 상세는 요청 당시 수량·전체 수량 희망금액·검수·승인·마켓 상태와 상품의 판매 등록·구매 예약·출고 확정 누적 수량을 구분한다. 상품번호로 마켓 URL을 추정하지 않으며 구매자 정보·관리자 메모·감사 이력은 공개하지 않는다.
- 기존 판매 요청 등록·상세 검수 완료·판매 승인 API는 유지한다. 검수·승인 완료 시각과 반려 사유는 현재 고객 공개 계약에 없어 표시하지 않는다. 자산명·단위는 현재 자산 정보이며 요청 당시 자산 전체 스냅샷으로 표기하지 않는다. 외부 DB·배포·커밋·푸시는 실행하지 않았다.

### 기존 자산 API 확장

| 항목 | 구현 계약 |
| --- | --- |
| 소유 범위·인증 | 기존 활성 CUSTOMER의 VIEWER·MANAGER 인증, 회사·소속·세션·접근 버전 검증을 유지한다. 회사 범위는 인증 정보로 결정하며 클라이언트 고객사 번호로 확장할 수 없다. 요청·상품은 조회 자산의 관계로만 읽는다. 타사 자산 상세는 기존404다. |
| 요청 존재·상태 | `GET /api/assets?saleRequested=true`. `false`는 요청 없는 자산, 생략은 기존 전체 자산이다. `saleRequestStatus=PENDING\|APPROVED\|REJECTED`, `saleInspection=PENDING\|COMPLETED`를 지원한다. 요청 전용 상태·기간·정렬은 `saleRequested=true`가 없으면400이다. |
| 검색·기간·정렬 | `q`는 최대160자로 기존 자산번호·자산명·규격·브랜드에 요청번호 검색을 추가한다(요청 조회 시). `saleRequestedFrom`, `saleRequestedTo`는 한국시간 날짜의 시작 포함·종료 다음 날 미포함이며 역전/유효하지 않은 날짜는400이다. `sort=requestedDesc`는 요청일 내림차순+자산번호 오름차순이다. `page`, `size`(최대100)와 기존 자산 조건·정렬을 유지한다. |
| 목록·상세 DTO | 기존 목록 `{success:true,data:Asset[],meta}`를 유지하고 각 자산에 `saleRequest` 또는 null을 추가한다. 기존 `GET /api/assets/{id}`도 동일 필드를 반환한다. 요청은 `id,status,inspection,quantity,desiredAmount,createdAt,product`만 공개한다. `quantity`는 기존 요청 당시 수량, `desiredAmount`는 전체 수량 희망금액이며 모두 Decimal 문자열이다. |
| 상품·판매 상태 | `saleRequest.product`는 없으면 null, 있으면 `id,status,publishedAt,listedQuantity,reservedQuantity,soldQuantity`다. 상품 상태는 `DRAFT/AVAILABLE/OUT_OF_STOCK`, 요청 승인·검수 및 자산 판매 상태와 별개다. OUT_OF_STOCK은 예약으로도 발생하며 판매 완료/정산 완료로 해석하지 않는다. 자산 `saleStatus=PENDING`을 요청 존재로 간주하지 않는다. |
| 전체 집계 | `saleRequested=true`에서만 최상위 `saleRequestSummary={approval:{PENDING,APPROVED,REJECTED},inspection:{PENDING,COMPLETED}}`를 추가한다. 인증된 고객사·검색어·요청 기간·기존 자산 조건 범위 전체를 대상으로 하며 페이지와 선택 승인·검수 필터는 무시한다. 목록 `meta.totalElements`는 선택 상태 필터도 적용한다. 0건 상태도 반환하며 RepeatableRead 트랜잭션으로 조회한다. |
| 공개 필드·회귀 검증 | 필요한 관계 필드만 Prisma select로 조회하고 전용 공개 DTO로 변환한다. 구매자 개인정보·신청자 번호·관리자 메모·감사 이력을 포함하지 않는다. 고객 OpenAPI/Scalar 스키마를 갱신하고 HTTP 입력/명세 테스트와 로컬 MySQL의 요청번호 검색·날짜 경계·페이지 독립 집계·상태 조합·정확한 수량/금액·타 고객사 격리·기존 평가금액 정렬을 검증한다. |

### 화면 동작 및 남은 범위

- 공통 `DetailSearch`의 검색·승인/검수·요청 기간 필터를 실제 API에 연결한다. 전체 상태 건수·목록 총건수·페이지 크기·이동·현재 페이지 CSV를 실제 응답으로 표시한다. CSV는 UTF-8 BOM과 수식 삽입 방어를 유지한다. 해당 탭에서는 보유 자산 요약 API를 호출하지 않는다.
- 로딩·조회 실패/새로고침·실제 요청 없음·검색 결과 없음·접근 불가를 구분한다. 화면 변경 시 이전 요청을 중단하고 오래된 응답이 덮어쓰지 않도록 한다. 모바일에서는 표만 가로 스크롤하고 상태·설명·버튼은 화면 안에 유지한다.
- 처리 완료 시각·반려 사유·요청 당시 자산명/단위의 별도 스냅샷·마켓 노출 가능 여부 및 상품 바로가기·상품 상태 전용 필터는 후속 계약으로 남긴다. 기존 `saleStatus` 조건은 자산 상태이며 상품 공개 상태 필터와 다르다. 취소·반려 처리·반려 후 재요청·수수료·정산·구매자별/분할 출고 이력은 별도 정책이 확정되기 전에는 추가하지 않는다.

### 자산 목록 다중 판매 요청

- 자산 목록 왼쪽 체크박스로 현재 페이지의 판매 가능한 자산만 선택한다(페이지 최대100건). 전체 선택은 판매 가능 자산만 포함하며 일부 선택 시 헤더 체크박스를 부분 선택으로 표시한다. 검색·페이지 크기·페이지 이동·새로고침·다른 화면 이동 시 선택을 초기화한다.
- 선택한 경우에만 작업줄의 선택 건수·평가 총액·판매 요청하기·선택 해제를 표시하고 선택 행을 강조한다. 평가 총액은 소수 수량을 정확하게 합산하고 미평가 건수를 별도로 표시한다. 희망금액·정산액·서로 다른 단위의 총수량으로 해석하지 않는다.
- 목록과 상세는 공통 `canRequestSale` 판정을 반환한다. 보관중·판매대기·S/A/B·양수 수량이고 기존 요청 및 연결 상품이 없는 자산만 선택 가능하다. 실제 접수 시 서버는 기존 인증·소유 범위·상태·수량을 다시 검증한다.
- 기존 판매 요청 입력창 스타일을 재사용하며 각 자산의 **전체 수량**에 대한 희망금액(1원~1조원 정수)을 입력한다. 평가금액은 자동 입력하지 않는다. 전송 전에 미접수 자산의 입력을 모두 검증한다.
- 기존 `POST /api/assets/{id}/sale-requests`를 순차 실행한다. 각 자산의 `{desiredAmount,expectedQuantity}`를 전송하며 일괄 트랜잭션이나 자동 롤백은 없다. 결과를 자산별로 표시하고 성공한 자산은 잠금 처리하여 재시도에서 제외한다. 일반 실패 및 중단으로 전송하지 않은 건만 수정·재시도한다.
- 수량 변경·중복·접근 불가 충돌은 확인 필요로 분리하고 재전송하지 않는다. 네트워크·서버 오류·잘못된 성공 응답 등 접수 여부가 불확실하면 이후 전송을 중단하고 해당 자산의 요청 내역을 확인한다. 세션 변경·만료 시에도 전송을 중단한다. 전송 중 닫기·중복 제출·로그아웃을 차단하고 페이지 이탈 시 경고한다.
- 닫으면 목록을 재조회하고, 판매 요청 내역 보기로 접수 내역을 확인한다. 자동 주기 새로고침으로 금액 입력이나 접수 결과를 없애지 않는다. 기존 요청 취소·반려 후 재요청 정책은 변경하지 않는다.

## 고객 포털 마이페이지 (2026-10-08)

- 1depth 메뉴는 내 자산, 마켓, 마이페이지로 구성한다. 자산 현황·자산 목록·판매 요청 내역은 내 자산 내부 탭이며 기존 계정 정보와 네 가지 이용 내역은 마이페이지로 통합한다.
- 마이페이지 내부 메뉴는 회원 정보, 입고 내역, 검수·폐기, 구매 견적, 주문·배송이다. 기존 이력 조회·상세·신청 후 이동과 업무 권한은 유지한다.
- 입고·검수는 신청 → 승인 → 입고·검수 → 결과 확인·폐기 동의, 구매·배송은 견적 요청 → 회신 → 승인·출고 요청 → 출고·배송 순서로 표시한다. 이는 절차 안내이며 개별 건의 현재 상태를 나타내지 않는다. 검수 결과 확인과 폐기 동의는 별도 업무다.
- 회원의 담당자명·연락처·이메일을 표시하고 수정·취소·입력 검증을 제공한다. 활성 VIEWER·MANAGER는 `PATCH /api/auth/me`로 본인 정보만 실제 DB에 저장한다. 새로고침 후에도 유지되며 이후 신청 담당자 기본값에 반영한다. 이미 저장된 신청·견적의 담당자 스냅샷은 변경하지 않는다.
- 이메일은 로그인 아이디다. 변경 시 현재 비밀번호를 확인하고 이메일을 소문자로 정규화하며 다른 계정과 중복되면409로 차단한다. 담당자명·연락처만 변경할 때는 비밀번호 입력을 요구하지 않는다. 비밀번호 자체는 변경하지 않는다.
- 저장 트랜잭션에서 계정·고객사 활성 상태, 소속·세션·접근 버전을 재검증한다. `version`은 현재 `sessionVersion`이며 동시 수정은 차단한다. 개인정보 변경과 비밀번호를 제외한 전후 감사 이력을 원자 저장한다. 성공 시 세션 버전을 증가시키고 현재 화면에 새 토큰·회원정보를 적용하며 기존 토큰은 폐기한다. 실패 시 입력을 유지하고 성공 표시를 하지 않는다.
- 고객사명·사업자등록번호·대표자·대표 연락처·주소와 회원 권한은 읽기 전용이다. 고객사 정보·소속·권한 변경은 MRS 문의로 연결한다.
- 기존 회원·감사 테이블을 사용하므로 신규 DB 마이그레이션은 없다. 외부 DB 적용·배포·커밋·푸시는 실행하지 않았다.

### 이용 내역 UI 정리 (2026-10-08)

- 입고 내역·검수·폐기·구매 견적·주문·배송을 공통 `목록 → 상세 → 목록` 구조로 정리했다. 각 메뉴는 쉬운 설명, 일반적인 진행 순서, 검색·초기화, 건수, 상태, 상세보기를 제공한다. 진행 순서는 개별 건의 현재 진행률이 아니며 반려·취소·분할 출고 등 예외 상태는 실제 응답으로 표시한다.
- 상세 화면의 목록 복귀는 항상 본문 상단 왼쪽 `목록으로` 버튼 하나로 제공한다. 입고 상세에서는 브라우저 이전 화면이 아니라 해당 입고 목록으로 복귀하며 검색·페이지 조건은 유지한다. 로딩·오류 중에도 목록으로 돌아갈 수 있다.
- 입고 상세는 신청 정보·자재 사진·처리 결과, 검수 상세는 검수 정보·자재별 결과·별도 폐기 동의, 구매 견적 상세는 회신 및 진행 상황·원래 요청 상품·요청 정보, 주문 상세는 확정 조건·출고 수량·배송별 진행 상황을 구분한다. 기존 조회·확인·동의·견적 승인·취소 API와 권한은 변경하지 않았다.
- 툴팁 디자인은 검수·폐기 목록의 `폐기 동의 안내` 한 곳에 시범 적용했다. 마우스 오버·키보드 포커스·클릭으로 열고, Esc·포커스 이탈·마우스 이탈로 닫는다. 검수 확인과 폐기 대상 동의, 비용 청구 동의가 별개임을 설명한다. 최종 배치 정책은 미확정이다.
- 목록에 데이터가 없을 때와 검색 결과가 없을 때의 안내를 구분한다. 모바일에서는 표 영역만 가로 스크롤하며 제목·설명·버튼·툴팁은 화면 안에 배치한다.

## 고객 업무 알림 (2026-10-08)

상단 종 아이콘으로 실제 고객 알림 목록을 제공한다. 같은 고객사 모든 활성 직원(작성자 포함)이 공유하며 읽음은 개인별로 DB에 유지된다. VIEWER도 읽음 처리할 수 있고 원 업무 승인·확인 권한은 바뀌지 않는다. 최근 90일만 조회하며 약 120초 visible 배지 갱신, 목록 진입·수동 최신 조회, 개별·모두 읽음, 전체·미읽음, 추가 페이지와 오류 재조회, 종별 실제 상세 이동·브라우저 뒤로가기를 지원한다. 읽음 실패는 성공으로 표시하지 않으며 상세 조회와 별개다. 대상 업무·정보 제한·신규 스키마·API·비동기성 정책은 [NOTIFICATIONS.md](NOTIFICATIONS.md)를 참고한다. 고객 포털 업무 알림만 구현했고 배송사·이메일·문자·푸시는 포함하지 않는다. 외부 DB 변경·배포·커밋·푸시는 수행하지 않았다.

## API

### 로그인 경계

- 고객: `/mrs2.0/`, `POST /api/auth/login`의 `{email,password}`, `GET /api/auth/me`, 세션 키 `mrs.auth.session`.
- 관리자: `/admin/`, `POST /api/admin/auth/login`의 `{id,password}`, `GET /api/admin/auth/me`, 세션 키 `mrs.admin.auth.session`.
- 고객 계정으로 관리자 로그인 또는 관리자 계정으로 고객 로그인을 할 수 없다. `aud`가 각각 `customer`/`admin`인 토큰을 발급하고 매 요청 현재 DB 역할·상태도 확인한다. 반대 영역 토큰과 `aud` 없는 구형 토큰은 401이다. 기존 사용자는 재로그인해야 한다.
- 고객 메뉴의 관리자 링크와 `#/admin` 자동 이동은 제거했다. 관리자 메뉴도 고객 포털 이동 링크를 제공하지 않는다. 관리자 HTML은 로그인 진입점이며, 실제 메뉴 모듈은 서버의 관리자 세션 확인 후 로드한다. 브라우저 저장소의 role을 바꾸는 것으로 권한을 얻을 수 없다.
- 공개 가입과 회원 소속 승인은 CUSTOMER만 처리한다. 관리자 계정은 서버 운영자가 직접 생성한다. 테스트 전용 `db:seed:admin`은 기존 고객 계정을 ADMIN으로 승격하지 않으며 재실행 시 기존 관리자 세션을 폐기한다. 운영용 관리자 생성·비밀번호 수명 정책은 별도 운영 절차로 관리한다.
- `admin/admin`은 격리된 로컬 테스트에만 사용한다. 운영 모드에서는 시드가 거부되며 공개 스테이징에서도 이 약한 계정을 사용하지 않는다. 이번 작업은 외부 DB와 배포에 적용하지 않았다.

관리 API는 MRS ADMIN만 접근 가능하다. 수정/심사/상태변경은 현재 version과 사유를 요구하고 충돌은 409다. 회원 version은 응답의 sessionVersion이다. reassign은 기존 세션을 폐기하고 PENDING/VIEWER로 바꾼다. 자산은 이동하지 않는다. 반려 회사 신청은 신청인을 PENDING 상태로 유지하고 수정 후 reopen 가능하다. 회원이 별도로 반려된 경우 회원부터 reopen한다.

본인 회원정보 수정은 고객 Bearer 토큰만 허용하며 대상 ID를 받지 않는다. 이름1~80자, 연락처8~20자(숫자·공백·괄호·하이픈 및 앞의 `+` 허용), 이메일 최대254자, 비밀번호8~128자, `version`은0 이상 정수다. 추가 필드·권한·소속 주입은400, 미인증·기존 토큰은401, 접근 권한 변경은403, 이메일 중복·버전 충돌은409다. 요청은8KB 이하이며 응답은 `no-store`다. 이메일 인증 메일·비밀번호 변경·고객사 편집은 이번 범위에 포함하지 않는다.

공개 검색·가입은 소켓 주소당 10분 120회, 검색 번호당 20회의 DB 공유 제한을 적용한다. 임의 X-Forwarded-For는 신뢰하지 않는다. 프록시 뒤에서는 동일 프록시 주소의 합산 제한이 적용되므로 실제 규모에 맞춘 신뢰 프록시 IP 전달/개별 제한 설정은 배포 전 점검 사항이다. 응답은 no-store이며 확인 결과 자체가 등록 여부를 일부 드러내는 잔여 위험은 존재한다.

이미지는 4.2MB 이하 PNG/JPEG/WebP base64 data URL만 인증 응답에 포함한다. 외부 저장소 URL을 임의 프록시하지 않는다. 기존 외부 이미지 URL을 보호된 저장소로 이관하기 전에는 해당 사진이 고객 화면에서 보이지 않는다. 입고/검수 연결의 고객사 불일치는 고객 조회를 503으로 차단한다. legacy 입고 문자열은 실제 FK라고 간주하지 않는다.

## 이관 및 배포 게이트

1. 백업을 확보하고 실제 migration 상태를 확인한다. `npm run customers:check`는 루트 환경 파일의 DB에 읽기 전용 보고서를 출력한다. 자동으로 실행하거나 운영 DB를 변경하지 않는다.
	`20260928000000_add_zone_location_hierarchy`는 원본 SQL·Git 이력·DB 적용 이력이 없는 미구현 작업의 빈 폴더로 확인되어 제거했다. 현재 위치 ID는 외부 참조이며 위치 계층 테이블은 만들지 않는다. 운영 이력은 삭제하거나 임의로 성공 처리하지 않는다. 격리 스키마 테스트만으로 배포 명령 검증을 대체하지 않는다.
2. 기존 고객사 코드별 실제 사업자·법인 매핑을 MRS가 확인한다. 회사명 또는 샘플 데이터로 자동 통합하지 않는다.
3. `20260930000000_add_customers`는 User/Asset/Receiving 코드 합집합을 동일 ID의 PENDING 고객사로 보존한 뒤 외래키를 연결한다. 기존 CUSTOMER/ACTIVE 회원은 PENDING으로 전환하고 개별 SUSPENDED/REJECTED는 유지한다. 자산 코드·수량·평가액은 수정하지 않는다.
4. 이관 대기 고객사에 정확한 사업자정보를 입력하고 사유를 남겨 활성화한다. 각 회원의 실제 소속을 확인해 별도 승인하고 재로그인한다. 고객사를 활성화하는 것만으로 회원이 활성화되지 않는다.
5. 이관 전후 고객사별 자산 건수·평가금액·단위별 수량을 비교한다. 입고·검수·자산 귀속 불일치와 활성 미연결 회원이 없음을 확인한다. 중복 실제 사업자의 코드 통합은 별도 검증된 데이터 이관으로 처리한다.
6. 신규 앱은 신규 스키마가 필요하다. 유지보수 시간에 DB→백엔드→관리자→고객 순서로 전환하고 기존 토큰은 재로그인한다. 실패 시 접근을 차단하고 백업/호환 앱 복구 계획에 따라 처리한다. 자동 파괴적 down migration은 하지 않는다.

현재 작업은 외부/운영 DB에 적용되지 않았다. 배포 대상은 별도 승인 시 스테이징 고객·관리자·백엔드이며 GitHub Pages는 제외한다.

## 검증

- backend: `npm run db:validate`, `npm run db:generate`, `npm run typecheck`, `npm test`, `npm run build`.
- 격리 MySQL: `RUN_CUSTOMER_SCHEMA_TEST=1 npx tsx --test test/customer-schema.test.ts`. 외부 DB 환경값을 사용하지 않고 임시 컨테이너/볼륨을 정리한다.
- 입고 회귀: `RUN_RECEIVING_SCHEMA_TEST=1 npx tsx --test test/receiving-schema.test.ts`.
- frontend: `npm run build`, `npm run lint`.
- 개발 프록시: `MRS_API_PROXY=http://127.0.0.1:3011 npm run dev -- --port 5185`.
- 비운영 테스트 관리자: backend에서 `npm run db:seed:admin`. 관리자 전용 `/admin/`에서 `admin` / `admin`으로 로그인한다. 이 명령은 `NODE_ENV=production`에서 실행을 거부하며 일반 고객 가입으로 ADMIN을 만들 수 없다.

## 후속 범위

입고·검수·판매·폐기·출고·정산·견적 저장 API, 실제 입고일/과금 기산일, 공개 마켓 API, 직원 셀프 승인, 다중 고객사 소속, 판매 후 소유권 이전은 포함하지 않는다. 기존 데모 업무 컴포넌트는 보존하지만 실제 고객 진입점은 CustomerWorkspace이며 샘플 업무 내역을 표시하지 않는다. 관리자 다른 업무 화면의 임시 편집은 별도 개발 범위다.
