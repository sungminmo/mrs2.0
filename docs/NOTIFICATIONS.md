# 고객 포털 업무 알림

## 수신 및 읽음 정책

- 같은 고객사에 현재 소속된 모든 활성 고객 직원이 동일한 업무 알림을 조회한다. 업무 작성자도 포함한다.
- 읽음은 직원 개인별이며 VIEWER·MANAGER 모두 처리할 수 있다. 검수 결과 확인·폐기 동의·견적 승인 등 원 업무의 권한이나 상태는 바꾸지 않는다.
- 도입 이후 성공한 업무만 기록한다. 과거 이력은 역생성하지 않는다.
- 서버 생성 시각 기준 최근 90일만 조회·읽음 처리한다. 입력된 과거 입고일은 조회 기간 기준이 아니다. 초기 구현에는 물리 삭제·정기 정리 작업이 없다.
- 관리자 알림, 이메일·문자·카카오톡·푸시, 배송사 연동은 제공하지 않는다.

## 생성되는 업무

| 업무 | 생성 시점 | 상세 대상 |
| --- | --- | --- |
| 입고 | 신청 접수, 승인, 반려, 실제 입고 완료 | 입고 신청 |
| 검수·폐기 | 결과 확정·정정, 고객 결과 확인, 폐기 대상 동의 | 검수 결과 |
| 판매 | 요청 접수, 판매용 상세 검수 완료, 승인·마켓 등록 | 해당 자산 |
| 구매 견적 | 접수, 회신 발송·철회·고객 거절 | 구매 견적 |
| 주문·출고 | 견적 승인, 출고 확정, 수기 배송 완료 | 주문 |
| 잔여 취소 | 고객 요청, 관리자 승인·거절, 관리자 직접 취소 | 주문 |
| 판매자 자산 | 실제 출고 시 자산별 출고 수량·잔여 수량 반영 | 판매자 자산 |

검수 결과의 폐기 대상은 같은 결과 알림 한 건에 포함한다. 검수 초안·회신 초안·출고 초안·재시도·실패·무변경 재확인은 알리지 않는다. 판매 승인은 실제 판매 완료·정산 완료가 아니다. 아직 API가 없는 판매 반려, 폐기 실행·비용 청구, 결제·정산의 알림은 생성하지 않는다. 회신 만료는 조회 시 계산하므로 자동 만료 알림도 없다.

## 저장과 부하

`notifications`는 고객사별 공유 이벤트, `notification_reads`는 실제 읽은 직원의 기록을 저장한다. 알림을 기존 업무 트랜잭션 안에서 저장하므로 알림 저장 실패 시 업무·감사·재고 변경도 롤백한다. `kind:customerId:업무 ID/버전/작업 ID` 고유 키로 중복 생성하지 않는다. 원 업무 삭제를 알림 FK가 막지 않도록 상세 대상에는 업무 FK를 추가하지 않는다.

별도 큐·Redis·WebSocket·SSE·워커·cron은 없다. 고객 탭이 보이는 동안 배지를 약 120~130초마다 조회한다. 숨김 전환 시 진행 중인 배지 조회를 취소하고 주기 조회를 중지한다. 화면 복귀 시 오래된 집계를 조회하며 알림 목록 진입·수동 새로고침은 최신 조회다. 즉시 전달·최대 지연 시간을 보장하지 않는다. 네트워크·서버 오류는 다음 조회 주기에 재확인하며 자동 mutation 재시도는 하지 않는다. 401·403은 자동 배지 조회를 중지한다. 조회 오류를 미읽음 0건으로 표시하지 않는다.

조회는 회사·기간 인덱스, 개인 읽음 반조인, `(createdAt DESC, id DESC)` keyset 페이지를 사용한다. 배지 조회에는 원 자산·견적 등의 상세를 조인하지 않는다. 알림 화면에서는 자산 목록 조회를 실행하지 않는다.

## API

공통: 활성 고객 인증, 현재 회사·소속·세션/고객 접근 버전 검증, `Cache-Control: private, no-store`. 고객사·사용자 식별자를 입력받지 않으며 미지정 필드를 거부한다. 응답은 `{success:true,data:...}`이다. 알림 번호는 unsigned BigInt의 십진 문자열이다.

| Method | Path | 입력·응답 |
| --- | --- | --- |
| GET | `/api/customer/notifications/summary` | 입력 없음. `{totalCount,unreadCount,windowDays:90,asOf}` |
| GET | `/api/customer/notifications` | `size=1..50`(기본20), `unreadOnly=true\|false`(기본false), `cursor?`. `{items,nextCursor,hasMore,windowDays:90}` |
| PATCH | `/api/customer/notifications/read` | `{ids:[중복 없는 십진 번호 1..100개]}`. 최신 집계 반환 |
| POST | `/api/customer/notifications/read-all` | `{}`. 최신 집계 반환 |

목록 항목은 `{id,kind,title,description,resourceCode,occurredAt,createdAt,readAt,target:{type,id}}`다. `target.type`은 RECEIVING·INSPECTION·ASSET·QUOTE·ORDER 중 하나이며 임의 URL은 없다. 상세 이동 시 해당 업무 API가 현재 접근 권한과 원본 존재 여부를 다시 검증한다. 읽음 실패가 상세 조회를 차단하지는 않지만 읽음 성공으로 가장하지 않는다.

선택 읽음에 타 고객사·없는 번호·90일 이전 번호가 하나라도 포함되면404로 전부 거부한다. 이미 읽은 번호는 최초 읽음 시각을 보존한다. 모두 읽음은 페이지·필터와 무관하게 해당 직원의 최근 알림 전체를 대상으로 한다. 짧은 ReadCommitted 트랜잭션의 `INSERT SELECT ... ON DUPLICATE KEY UPDATE`가 보는 알림에만 실제 읽음 기록을 생성한다. 단순 최고 ID watermark는 사용하지 않는다. 늦게 커밋된 낮은 ID나 처리 후 신규 알림은 자동으로 읽히지 않으므로 처리 응답의 미읽음이 0이 아닐 수 있다. 응답 유실 시 자동 재시도하지 말고 최신 집계를 조회한 후 새 사용자 의도로 처리한다.

## 정보 제한 및 적용

제목·설명은 고객 공개 내용만 저장한다. 관리자 메모·감사 JSON·담당자 연락처는 복사하지 않는다. 판매자 출고 알림은 자사 자산 번호·상품명·출고/잔여 수량만 포함하고 구매자·주소·가격·주문 상세를 노출하지 않는다. 소속이 바뀌거나 고객사/직원이 정지되면 이전 회사의 조회·읽음은 차단된다.

신규 마이그레이션은 `20261008000000_add_customer_notifications`이며 두 테이블만 추가한다. 기존 업무 자료·재고의 backfill은 없다. 이 구현의 적용·통합 검증은 로컬 격리 MySQL에서만 수행하며 외부 DB 변경·배포는 별도 승인 절차를 따른다. 실행 OpenAPI의 `Notifications` 태그가 최신 요청·응답 스키마를 제공한다.

격리 테스트는 `MRS_NOTIFICATION_TEST_DB_PORT`, `MRS_NOTIFICATION_TEST_DB_NAME`, `MRS_NOTIFICATION_TEST_DB_PASSWORD`를 명시하고 `backend/node_modules/.bin/tsx --test backend/test/notification.test.ts`로 실행한다. 호스트는127.0.0.1로 고정하며 테스트/미리보기 이름의 DB만 허용한다. 테스트가 전용 회사·계정·업무 자료를 생성하고 정리한다.
